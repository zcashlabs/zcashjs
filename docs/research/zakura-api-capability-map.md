# Zakura symbol-level wallet capability map

Current integration: [transaction/query plan](../planning/transaction-query-api.md) and [WASM host architecture](../planning/wasm-host-architecture.md) govern DTOs, exact-byte extension outbox, scanner liveness and refined D07. “Verified” below means inspected source only. Functional qualification precedes all performance work, which is deferred to the tracked benchmark issue #11.

Research snapshot: 2026-09-04. Scope: **transparent + Sapling + Ironwood**. Public zcash.js names, including `send`, `wait`, `propose`, `prove`, `sign` and `finalize`, remain **PRELIMINARY**. This is source inspection, not a build, runtime test, network-activation claim or device compatibility result. [D06 remains Open](../planning/decision-log.md). Preserve the other owner decisions, including Rust-owned SQLite, host-owned transport, external signer seams, and deferred Sprout and remote proving.

The source contains explicit Ironwood coverage across keys/receiver reuse, compact scanning, SQLite, selection, building, PCZT signing/proving and extraction. It does **not** establish a complete deployed transparent + Sapling + Ironwood wallet: the two checked-out repositories describe different Common versions, the standard proposal-to-PCZT entry point only accepts one step, and host transport, durable recovery and send-and-wait orchestration still need validation.

## Actual Ironwood identity and migration boundary

* Public `orchard::ValuePool::Ironwood` and `ProtocolVersion::V3` are explicit variants ([C/crates/orchard/src/lib.rs:177](https://github.com/zakura-core/common/blob/13360888be437f066da5e16242663d1b211c6f87/crates/orchard/src/lib.rs#L177)). `bundle::BundleVersion::ironwood_v3()` selects that pool, `NoteVersion::V3` and `OrchardCircuitVersion::PostNu6_3`; `orchard_v3()` remains the **different Orchard pool**, using V2 notes and its cross-address restriction. [C/crates/orchard/src/bundle.rs:108](https://github.com/zakura-core/common/blob/13360888be437f066da5e16242663d1b211c6f87/crates/orchard/src/bundle.rs#L108).
* `note_encryption::IronwoodDomain` is the V3 encryption/decryption domain, distinct from `OrchardDomain`; V3 uses plaintext lead byte `0x03`. [C/crates/orchard/src/note_encryption.rs:196](https://github.com/zakura-core/common/blob/13360888be437f066da5e16242663d1b211c6f87/crates/orchard/src/note_encryption.rs#L196). Shared `Address`, `SpendingKey`, FVK and Merkle node shapes do not merge pools.
* Unified addresses have an Orchard receiver, not a new `Receiver::Ironwood`. `Address::can_receive_as` explicitly maps Ironwood to the Orchard receiver ([C/crates/zcash_keys/src/address.rs:447](https://github.com/zakura-core/common/blob/13360888be437f066da5e16242663d1b211c6f87/crates/zcash_keys/src/address.rs#L447)). Wallet selection assigns that receiver to Ironwood at the configured activation context ([B/src/data_api/wallet/input_selection.rs:991](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/librustzcash/zcash_client_backend/src/data_api/wallet/input_selection.rs#L991)); shielding's private `resolve_shielded_destination` does the same. This is source-verified receiver reuse, not inference from the name Orchard.
* Backend `wallet::Note::Orchard` carries a `pool: orchard::ValuePool`; `ReceivedNotes::ironwood` is separately tracked, despite sharing `orchard::Note`. [B/src/data_api.rs:1162](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/librustzcash/zcash_client_backend/src/data_api.rs#L1162); [B/src/data_api.rs:1313](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/librustzcash/zcash_client_backend/src/data_api.rs#L1313). Preserve pool tags in every host DTO, note ID, output index, nullifier and balance.
* Primitives `TxVersion::V6` carries separate Orchard and Ironwood slots. `Builder` tests the branch and `has_ironwood`; Ironwood is not a v5 extension ([C/crates/zcash_primitives/src/transaction/builder.rs:910](https://github.com/zakura-core/common/blob/13360888be437f066da5e16242663d1b211c6f87/crates/zcash_primitives/src/transaction/builder.rs#L910)). `BranchId::Nu6_3` and target-height parameters are the source context; no live network/activation height was verified. Experimental `zcash_unstable="nu7"` / `zip-233` is separate from this NU6.3 path.
* Post-activation Orchard-to-Ironwood crossing is a real migration behavior, not a rename: `propose_transfer` contains canonical-crossing selection logic ([B/src/data_api/wallet.rs:827](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/librustzcash/zcash_client_backend/src/data_api/wallet.rs#L827)), and SQLite retains migration tables plus distinct Ironwood notes/tree schema. [S/src/wallet/init/migrations/orchard_ironwood_migration_unsatisfiability.rs:1](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/librustzcash/zcash_client_sqlite/src/wallet/init/migrations/orchard_ironwood_migration_unsatisfiability.rs#L1). Schema migrations are distinct from moving funds between pools. Ordinary Ironwood use must preserve this distinction; automatic legacy-fund migration and its external `zcash_pool_migration` orchestration remain outside the demonstrated initial-scope flow.

## Capability map

Classification concerns the Rust capability at the inspected source, **not released JS availability**. **Direct** = directly available public Rust operation; **Composition** = available by composing existing Rust operations; **Wrapper** = needs a thin zcash.js Rust-host wrapper for lifecycle/traits/DTOs; **JS/network** = network/JS responsibility; **Unverified** = missing or unverified at the required scope. Rows can split an existing primitive from missing product behavior. Features are incremental to each crate's ordinary dependencies; `B:orchard`, `S:orchard`, `P:orchard` include the explicit Ironwood paths described above.
