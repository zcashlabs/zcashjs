## WASM-first runtime and storage (D07 refinement; D03a deferred)

The owner's latest direction refines D07’s Node implementation detail while preserving Rust-owned Zakura SQLite and D04–D25’s other settled constraints. Both runtimes start with bundled SQLite in the wallet WASM instance; Node supplies a filesystem VFS and browsers an OPFS VFS. A separate native SQLite connection cannot be injected across unrelated WASM/native memories for free. N-API/native acceleration is a future measured-budget decision, not a current delivery promise.

The [host architecture](wasm-host-architecture.md) specifies the baseline/threaded artifacts, Node worker_threads/shared Rayon qualification, secure isolated-browser SAB selection, no-SAB scanner/VFS fallback, serialized database ownership, handle/buffer contracts and functional gates. Earlier host-owned IndexedDB alternatives and native-Node defaults are superseded planning alternatives, not active recommendations.

The asterisk marks implementation risk: the earlier spike compiled a mixed published graph, not the selected full Common 1.0.0 graph; its real SQLite link probe remained unresolved at `sqlite3_os_init`. No final wallet-module instantiation, scanner liveness or durable Node/browser VFS has been demonstrated. Require close/destroy/reopen and crash/migration/single-writer proofs before durability claims. If the exact pinned adapter proves impractical, revisit the adapter/backend with evidence while preserving the public API.

## Transaction/query integration under existing decisions

The [transaction/query plan](transaction-query-api.md) concretizes D09/D14/D21: ordinary `send({ accountId, to, amount }) → PendingPayment → wait()`, explicit account identity and attached or supplied signer; `send({ proposal })` executes exactly the reviewed plan. Local creation is fused and supports Zakura’s actual multi-step dependencies. Advanced build/prove/sign/finalize are single-step PCZT semantics, preserving approved `wallet.pczt` and `operations` namespaces.

Operation/outbox persistence, exact-byte retry, revisions, full inventory/history projections and complete enhancement-aware sync are new product glue over source primitives, not existing Zakura pending/query APIs. Use Rust-owned schema-pinned projections and valid extension transactions/external migrations. Public accounts use `viewOnly`; v1 Pool remains transparent/Sapling/Ironwood with explicit unsupported legacy accounting. These refinements preserve D04–D25 except the expressly updated D07 runtime choice; names/signatures outside settled namespaces remain planning candidates.

## Transport architecture (D08 — Decided)

Use the retained [network-interface evidence](../research/zakura-common-landscape.md#network-interfaces-that-must-be-validated-individually). These choices concern orchestration and deployment, not an assumption that indexers, node RPCs and wallet daemons expose interchangeable methods.

| Option | Benefits | Costs / validation needed |
| --- | --- | --- |
| Host-side adapters: lightwallet protocol for sync, explicit node JSON-RPC for applicable public queries; Node gRPC and browser gRPC-Web/gateway implementations | Fits one TypeScript API while keeping endpoint policy, credentials, cancellation and streaming outside crypto. Recommended starting direction. | More than one wire adapter; validate protobuf revision, deployed methods, Sapling and Ironwood scan/transaction data, browser streaming/proxy/CORS and per-method trust semantics. A gateway is a real deployment requirement, not automatically available. |
| Rust-owned networking reused from wallet/backend stacks | Could reuse existing orchestration and codecs where compatible. | Couples runtime/network authority to wallet engine; target-specific async runtimes and browser hosting need probes. Makes host customization and privacy policy harder unless a clear injection boundary exists. |
| Required application gateway with one custom HTTP/streaming contract | Can simplify client deployment interfaces and centralize protocol translation/authentication. | Introduces server operations, availability, schema maintenance and another observer of queries. Risks requiring infrastructure for ordinary Node use. Keep as an optional adapter unless an evidenced product requirement justifies making it mandatory. |

Use protocol-typed host adapters and lazy network-only public queries. Public clients use `http(url)` for the supported node JSON-RPC contract. Standard light clients use `grpc(url)` for the protobuf lightwallet contract; the adapter selects native gRPC on Node and browser-compatible gRPC-Web mechanics where supported without exposing separate constructors. Validate the selected endpoint with one harmless protocol handshake when the client first connects, rather than requiring callers to declare method-by-method capabilities. Custom light transports may implement the same client transport interface. A composed Zcash client namespaces shared instances under `public`, `light` and `wallet`; each constituent client also remains independently constructible and injectable. Composition must enforce one network identity and must not duplicate injected client state or assume ownership of externally managed resources.

zcash.js will not operate or require its own node, lightwallet server or custom gateway. Applications supply endpoints directly or through optional external provider presets. Node gRPC, browser gRPC-Web or third-party gateway support are transport adapters, not a reason to collapse the protocol boundaries. A lightwallet handshake uses its standard server-info method; a node handshake uses a harmless identifying/chain-info RPC selected for the supported node contract. If the endpoint does not match, fail at connection with a protocol or network mismatch. Optional methods can still return a normalized method-not-supported error when called; do not expose a large boolean capability manifest as required configuration.

Settle endpoint/network identity, authentication, schema/version negotiation, supported pools/methods, TLS/CORS, deadlines, backpressure, reconnect/resume, pruning and malformed responses. Record disclosure per request, including transparent-address queries, viewing data and endpoint failover; switching servers can change privacy exposure and must follow explicit policy. Validate Sapling and Ironwood coverage separately rather than assuming existing compact schemas suffice.

Reads can have bounded retry policies; a timed-out broadcast must retain an unknown outcome and finalized transaction identity/bytes. Reconcile through observation before any policy-approved rebroadcast of the same bytes; never blindly construct a new spend. Acceptance, mining, confirmation depth, reorg and expiry remain distinct. Assign a transport/privacy reviewer at G0 and resolve D08 through G3–G5 evidence.

## Transaction and signer review contract (D09, D11 — Direction and Decided)

Specify a state model before signatures or names: intent/proposal, reviewable plan, protocol-valid construction/PCZT roles, proofs and authorization in permitted order, finalization, submission and observation. A plan may yield multiple transactions; model partial progress and per-transaction identity. Lower-level operations and composed operations must share the same invariants and reviewed-plan identity.

The proposed typed pending handle should retain identity and submission evidence, including an unknown outcome when the response is lost. Its proposed wait behavior needs confirmation policy, reorg/expiry results, timeout/cancellation, resumable observation and partial-payment semantics. Cancelling observation cannot undo a broadcast. Composed operations must surface disclosures and external signer review before affected actions, and must not turn an unknown submission into a definite failure or success.

External signer capabilities must describe supported roles, pools, transaction/circuit versions and required review data. PCZT interchange, redaction, commitment checks, proof/sign ordering and final extraction need end-to-end validation with exact Common/wallet APIs. Ledger/Vizor prior art motivates this seam now; concrete Ledger support is a documented unsupported placeholder pending later qualification. Remote proving remains deferred.

Open choices have no invented owners, deadlines or benchmark outcomes. The workplan assigns reviewers at G0 and records evidence and disposition at the relevant gates. A later scope change should update this log and the affected capability rows together.
